# 아키텍처 리뷰: 워크플로우 기반 재구성 vs 현재 도메인 기반

> 작성일: 2026-04-17
> 상태: 리뷰 완료, 논의 중

## Context
기존 10개 도메인팀 구조(principles, daily_briefing, macro, technical, ...)에서
7개 워크플로우 Agent 구조(수집 → 교육 → 실전매매 → 알림 → 수동 → 피드백 → 고도화)로
재구성을 검토 중. "각개 전투" 느낌이 든다는 것이 동기.

---

## 1. 핵심 판단: 기존 vs 제안

### 기존 방식의 문제점 (사용자 지적이 맞는 부분)
- 10개 팀이 **파이프라인 없이 나열**되어 있어 데이터 흐름이 불명확
- "매크로팀"이 데이터 수집도 하고 분석도 하고 → 역할 경계가 모호
- 공통 수집 로직이 팀마다 중복될 가능성
- 팀 수가 너무 많아 혼자 관리하기 어려움

### 하지만 제안 방식에도 문제가 있음

**문제 1: "투자Advisor Agent"가 너무 크다**
- Task 1~6이 전부 다른 도메인 (매크로, 단기테마, 종목, 매매, 계좌, 원칙)
- 이걸 하나의 Agent로 묶으면 결국 **내부에서 각개 전투**가 반복됨
- Agent 안의 Task가 사실상 기존의 "팀"과 동일한 크기

**문제 2: "수집"과 "분석"의 분리가 과도**
- 수집 Agent가 모든 데이터를 모아놓고 → 분석 Agent가 읽는 구조
- 그런데 Task3(강세섹터/주도주 판단)은 이미 **분석이 포함된 수집**
- 수집 시점에 LLM 판단이 필요하다고 적혀 있음 → 경계가 흐릿

**문제 3: 교육/페르소나 레이어의 오버엔지니어링**
- "IQ 점수", "양질도 10점 채점", "웹검색 크로스체크" → 이것만으로 한 프로젝트 분량
- 핵심 목표(매매 가이드 받기)에 도달하기 전에 인프라에 매몰될 위험
- 페르소나/시스템프롬프트는 **MD 파일 + 수동 편집**으로 충분히 시작 가능

## 2. 추천: 하이브리드 구조 (3-Layer Pipeline)

기존의 팀 격리 원칙을 유지하되, **파이프라인 3단계**로 묶는 방식:

```
Layer 1: 수집 (Collect)        — 데이터만 모은다. 판단 없음.
Layer 2: 분석 (Analyze)        — 수집된 데이터로 판단한다.
Layer 3: 행동 (Act)            — 분석 결과로 알림/기록한다.
```

### 구체적 팀 구성 (10개 → 6개로 축소)

| Layer | 팀 ID | 역할 | 타입 |
|-------|--------|------|------|
| **Collect** | `market_data` | 시세, 환율, 금리, ETF 등 수치 데이터 수집 | code-only |
| **Collect** | `news_scanner` | 뉴스/시황 수집 + 분류 (장기/단기 태깅) | llm-based |
| **Analyze** | `macro_analyst` | 매크로 + 시황 종합 판단 | llm-based |
| **Analyze** | `stock_analyst` | 종목/섹터 분석 + 매매 시그널 | llm-based |
| **Analyze** | `risk_manager` | 원칙 준수 + 계좌 리스크 체크 | hybrid |
| **Act** | `briefing` | 종합 브리핑 생성 + 알림 발송 | llm-based |

### 왜 이게 나은가:
1. **팀 수가 관리 가능** (6개, 혼자 감당 가능)
2. **파이프라인이 명확** (수집→분석→행동, 3단계)
3. **기존 인프라 100% 재활용** (StandardOutput, team_outputs, orchestrator, memory, knowledge)
4. **교육 레이어 불필요** — persona.md + compiled.md가 이미 이 역할을 함
5. **팀 격리 유지** — 각 팀은 여전히 독립적, DB로만 소통

### 실행 순서 (Orchestrator가 관리):
```
Wave 1: market_data + news_scanner  (병렬, 수집)
Wave 2: macro_analyst + stock_analyst  (병렬, 분석, Wave 1 의존)
Wave 3: risk_manager  (Wave 2 의존)
Wave 4: briefing  (Wave 2+3 의존, 최종 출력)
```

## 3. 핵심 질문에 대한 답변

### Q1: LLM API vs 로컬 Claude Code 프로세스?
**→ API 사용이 맞다.**
- Claude Messages API에서 `system` 파라미터로 페르소나/시스템프롬프트 부여 100% 가능
- Prompt Caching으로 system 블록 비용 90% 절감 (이미 core/llm에 구현됨)
- 로컬 Claude Code는 개발 도구이지, 런타임 서비스용이 아님
- API 키 하나면 팀별로 다른 system prompt 자유롭게 주입 가능

### Q2: Agent 간 긴밀한 소통이 가능한가?
**→ "긴밀한 소통"의 정의를 재설정해야 한다.**
- 사람처럼 실시간 대화하는 구조는 **비용 폭발 + 디버깅 불가능**
- 대신 **구조화된 데이터 전달** (StandardOutput)이 훨씬 안정적
- 각 팀이 DB에 판단을 남기고, 다음 팀이 그걸 읽는 **배치 파이프라인**
- 이게 "긴밀"하지 않아 보이지만, **재현 가능하고 디버깅 가능**한 유일한 방법
- 실제 금융 시스템도 이렇게 동작함 (메시지 큐 기반 파이프라인)

### Q3: 이 프로젝트가 의미 있는가?
**→ 범위를 좁히면 의미 있다.**
- 현재 제안은 **전체 증권사 시스템** 수준의 범위
- 혼자 하려면: **"매일 아침 시황 브리핑 + 관심종목 알림"** 하나만 먼저 완성
- 그것만 해도 실용적 가치가 충분
- 매매일지, IQ 점수, 교육 시스템, 4계좌 관리는 **후순위**

### Q4: LLM 판단의 신빙성 검증?
**→ 백테스팅 + 인간 피드백 루프**
- LLM 판단을 team_memory에 저장 → 나중에 실제 결과와 비교
- confidence 점수와 실제 적중률의 캘리브레이션
- 처음부터 자동화하지 말고, **사람이 읽고 판단**하는 것부터 시작
- "AI가 매매 결정" 이 아니라 "AI가 자료 정리 + 관점 제시"가 현실적 목표

## 4. 점진적 구현 로드맵 (혼자 하는 기준)

### Phase 1: 수집 파이프라인
- [ ] KIS API MCP 서버 구축 (시세, ETF, 거래대금)
- [ ] `market_data` 팀: 환율, 금리, 지수 수집 → DB 저장
- [ ] 수동 트리거 API + 스케줄러 자동 수집
- [ ] 어드민 화면: 수집 데이터 조회

### Phase 2: 분석 파이프라인
- [ ] `macro_analyst` 팀: 매크로 데이터 → LLM 판단
- [ ] `stock_analyst` 팀: 섹터/종목 → LLM 판단
- [ ] persona.md + compiled.md 작성 (교육 시스템 대신)

### Phase 3: 출력 파이프라인
- [ ] `briefing` 팀: 종합 → 텔레그램 발송
- [ ] 웹 대시보드: 브리핑 히스토리 조회

### Phase 4: 리스크 + 매매 기록
- [ ] `risk_manager` 팀: 원칙 체크 + 계좌 관리
- [ ] 매매일지 스키마 + 기록 API

### Phase 5: 고도화 (ongoing)
- [ ] 판단 적중률 추적
- [ ] 페르소나 튜닝
- [ ] 수동 모드 (skill or API)
